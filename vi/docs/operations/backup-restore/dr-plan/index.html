Disaster recovery plan for node1

What has to survive, how much loss and downtime is acceptable, and how each piece gets back. The mechanics of the nightly job are in Backing up the cluster; the rebuild steps are in infra/backup/RESTORE.md.

History: what the 2026-10-31 audit found

The nightly job had been running and succeeding for weeks, yet nothing had ever left node1 (the upload half of the backup flow was never installed), postgresql-ha had never been dumped (backup.sh listed only clusters that were not deployed, and skipped them silently), and the volume tarballs were of empty, retired directories. Fixed the same day — steps 1–4 below; the first off-site run is node1/*/20261031-131322.

4. Architecture​

node1                                     AWS ap-southeast-1
─────
02:30 cluster-backup.timer                s3://tiktuzki-cluster-backup
  backup.sh   → /srv/k8s-volumes/backups    Object Lock governance 30 d, versioning, SSE-S3,
                (staging, keep 7)           public access blocked, TLS only
  cluster-backup upload  ── age ──────►     node1/critical/…tar.zst.age   STANDARD_IA, expire 400 d
                                            node1/bulk/…tar.zst.age       STANDARD_IA, expire 90 d
Spilo (every postgresql-ha pod)           s3://tiktuzki-pg-wal
                                            versioning, deleted versions kept 30 d, SSE-S3, TLS only
  WAL-G: each WAL segment ── libsodium ►    spilo/postgresql-ha/wal/…
         daily base backup 01:00      ►     spilo/postgresql-ha/basebackups/…

Two buckets, because WAL-G cannot write to a locked one. A bucket with default Object Lock retention rejects any upload without Content-MD5 or a CRC checksum; cluster-backup (aws-sdk-s3 1.119) sends CRC32, Spilo's WAL-G (aws-sdk-go v1) sends neither. The WAL bucket gets the same guarantee another way: versioning, and a WAL-G user with DeleteObject but no DeleteObjectVersion or lifecycle/versioning permissions — a compromised node1 can hide objects behind delete markers, never destroy a version younger than 30 days.

Two IAM users, one per writer:

UserAllowed onActionsCannot
node1-cluster-backuptiktuzki-cluster-backup/node1/*PutObject, AbortMultipartUpload, GetObject (upload verification)list, delete, write anywhere else
node1-walgtiktuzki-pg-walPutObject, GetObject, ListBucket, DeleteObjectpurge versions, change versioning or lifecycle, touch the archive bucket

Both are created by infra/backup/aws-setup.sh, which writes their access keys straight into Proton Pass (pass://athena/node1-backup-s3, pass://athena/node1-walg-s3) and then proves every allow and deny with the new keys.

Encryption is client-side for both paths, so a leaked bucket is ciphertext: age for the nightly archives (node1 holds only the public key), libsodium (WALG_LIBSODIUM_KEY, a sealed secret) for WAL-G.

Cost: under 1 GB in total; well under US$1/month.

Changes from the original backup-flow.md design: the bulk half goes to STANDARD_IA daily instead of DEEP_ARCHIVE weekly. It is megabytes, so Deep Archive's 180-day minimum and 12–48 h thaw buy nothing and cost a day of RPO.

7. Restore paths, in brief​

  • Postgres to a point in time — Spilo clone: a new cluster with CLONE_METHOD=CLONE_WITH_WALE, CLONE_TARGET_TIME, the same bucket and libsodium key. Verify, then point pgdog at it or swap names. Detailed runbook comes with step 5.
  • Postgres, simplest — pg_dumpall file from last night's bulk half → psql into any Postgres 18.
  • Whole node — RESTORE.md: critical half first (sealed-secrets key, CA, secrets), Argo re-syncs from Git, then Postgres from WAL-G, then PV tarballs.
